# TuitionTrack Database Design & Interview Report

Project: TuitionTrack  
Stack: MongoDB Atlas, Mongoose, Express.js, React, Node.js  
Database style: NoSQL document database with Mongoose schemas and application-level relationships

---

## 1. Project overview

TuitionTrack is a tuition/coaching management web app made for a teacher or small coaching owner. The main goal of the database is to store and manage:

- teacher account and login data
- student records
- monthly fee status
- daily attendance
- expenses
- reminder history for fee follow-ups
- configurable reminder message templates

The backend uses MongoDB through Mongoose. MongoDB stores data in collections, and each record is stored as a document. Mongoose is used on top of MongoDB to define schemas, validations, relationships, indexes, and helper methods.

In interview language:

> I used MongoDB because my project data is naturally JSON-like and changes quickly during development. Since the app is built with MERN, MongoDB fits well with Express and React because the same object structure can move from database to backend API to frontend UI. I used Mongoose to add schema validation, references, indexes, and model-level logic.

---

## 2. Why MongoDB was chosen

MongoDB was selected because TuitionTrack is a MERN project and most of the data is document-friendly. A student record, fee record, attendance record, and notification record can all be represented as JSON objects.

### Main reasons

1. Flexible schema

   During learning and development, the data model changed multiple times. For example, reminders first used email, then moved toward WhatsApp/manual reminders. MongoDB made it easier to evolve fields without heavy migrations.

2. MERN compatibility

   MongoDB documents are JSON-like. The backend sends JSON APIs, and React consumes JSON. This reduces mental overhead while learning full-stack development.

3. Fast CRUD development

   Student CRUD, fee CRUD, attendance marking, and expense CRUD are simple to build using Mongoose methods like `find`, `create`, `findByIdAndUpdate`, and `deleteMany`.

4. Good for small-to-medium app scale

   For a coaching management app, MongoDB Atlas free tier is enough for demo and learning usage. Later, indexes and pagination can support growth.

5. Mongoose adds structure

   MongoDB itself is flexible, but this project still needs rules. Mongoose provides required fields, enums, min/max validation, regex validation, password hashing hooks, timestamps, and indexes.

### Honest interview point

MongoDB does not mean "no structure". In this project, I still designed clear collections, relationships, validation rules, and indexes. Mongoose helped me keep the database disciplined.

## 3. Database architecture

The database is organized around one main owner: the teacher.

Each teacher has their own students, fee records, attendance records, expenses, and notification logs. Most collections include `teacherId`, which connects the data to the logged-in teacher.

This is important because if multiple teachers use the app in the future, one teacher should not be able to see another teacher's data.

### High-level relationship diagram

```text
Teacher
  |
  |-- Student
  |     |
  |     |-- FeeRecord
  |     |
  |     |-- Attendance
  |     |
  |     |-- NotificationLog
  |
  |-- Expense
```

### DBMS relationship meaning

- One teacher can have many students.
- One student can have many monthly fee records.
- One student can have many attendance records.
- One student can have many notification logs.
- One teacher can have many expenses.

In DBMS terms, this is mostly a one-to-many relationship design.

## 5. Teacher collection

The Teacher collection stores login and account-level data.

### Main fields

| Field | Type | Purpose |
|---|---|---|
| `_id` | ObjectId | Primary unique identifier generated by MongoDB |
| `name` | String | Teacher's name |
| `email` | String | Login email |
| `password` | String | Hashed password |
| `reminderTemplates` | Object | Custom reminder messages |
| `createdAt` | Date | Auto-created by timestamps |
| `updatedAt` | Date | Auto-updated by timestamps |

### Important design points

The email field is unique, so two teachers cannot register with the same email. The password is not stored as plain text. Before saving, Mongoose runs a `pre("save")` hook and hashes the password using bcrypt.

The password field has `select: false`, which means it is not returned by default in queries. This reduces accidental password hash exposure.

The schema also has `comparePassword`, a model method used during login. It compares the entered password with the hashed password.

### Interview explanation

> For authentication, I created a Teacher model. I store the password as a bcrypt hash, not plain text. I also set `select: false` on the password field so it is not returned accidentally. During login, I explicitly select the password and use bcrypt compare. After login, I generate a JWT token. The teacher's `_id` from the token is then used to scope all database queries.

The Student collection stores the core student profile.

### Main fields

| Field | Type | Purpose |
|---|---|---|
| `_id` | ObjectId | Primary unique identifier |
| `teacherId` | ObjectId ref Teacher | Owner of this student |
| `name` | String | Student name |
| `phone` | String | Student phone |
| `parentName` | String | Parent/guardian name |
| `parentPhone` | String | Parent phone number |
| `parentEmail` | String | Parent email, optional |
| `class` | String enum | Class tag: 9, 10, or 11 |
| `feeAmount` | Number | Monthly tuition fee |
| `feeDueDate` | Number | Due day of month, e.g. 5 |
| `address` | String | Address |
| `joinedAt` | Date | Joining date |
| `createdAt` | Date | Auto-created |
| `updatedAt` | Date | Auto-updated |

### Validation

- `name`, `phone`, `parentName`, `parentPhone`, `class`, `feeAmount`, and `feeDueDate` are required.

```text

compound index: teacherId + class + name
```

This helps with queries like:

- filter by class
- search/sort students by name inside a class

### Interview explanation

> I kept student data in a separate collection because it is the central entity of the app. Fee records, attendance, and reminders are linked to students through `studentId`. I also store `teacherId` in every student document so each teacher's data remains isolated.

## 7. FeeRecord collection

The FeeRecord collection stores monthly fee status for each student.

### Why a separate collection?

At first, it might look easy to store fees inside the Student document. But that would make the student document grow every month forever.

Example of bad design:

```text
Student
  fees: [
    January fee,
    February fee,
    March fee,
    ...
  ]
```

This becomes harder to query, update, index, and analyze over time.

So TuitionTrack uses a separate `FeeRecord` collection. Each document represents one student's fee for one month.

### Main fields

| Field | Type | Purpose |
|---|---|---|
| `_id` | ObjectId | Primary unique identifier |
| `teacherId` | ObjectId ref Teacher | Owner teacher |
| `studentId` | ObjectId ref Student | Student linked to this fee |
| `month` | String | Month in `YYYY-MM` format |
| `amountPaid` | Number | Amount paid by student |
| `amountDue` | Number | Expected/remaining fee amount |
| `paidOn` | Date | Payment date |
| `status` | String enum | `paid`, `partial`, or `due` |
| `receiptNumber` | String | Generated receipt number |
| `createdAt` | Date | Auto-created |
| `updatedAt` | Date | Auto-updated |

### Validation

- `month` must match `YYYY-MM`, such as `2026-08`.
- `amountPaid` cannot be negative.
- `amountDue` cannot be negative.
- `status` must be only `paid`, `partial`, or `due`.

### Unique compound index

```text
teacherId + studentId + month must be unique
```

This is one of the most important database constraints in the app.

It prevents duplicate fee records for the same student in the same month.

Example:

```text
Student: Aarav
Month: 2026-08
Allowed: only one fee record for this combination
```

### DBMS principle used

This is similar to a composite unique key in SQL.

In SQL, we might write:

```sql
UNIQUE (teacher_id, student_id, month)
```

In MongoDB/Mongoose, we use:

```text
feeRecordSchema.index({ teacherId: 1, studentId: 1, month: 1 }, { unique: true })
```

### Interview explanation

> FeeRecord is separate from Student because fees are monthly transactional data. I used a compound unique index on teacherId, studentId, and month to make sure one student cannot have duplicate fee records for the same month. This keeps the fee data consistent.

## 10. NotificationLog collection

The NotificationLog collection stores reminder history.

Originally the project had email reminder planning, but the practical decision was changed because SMS/WhatsApp automation through providers like Twilio is paid. So the project moved toward a cost-friendly reminder system:

- backend calculates due/upcoming/overdue students
- teacher sees reminder queue
- teacher opens WhatsApp manually with a predefined message
- system logs the action

This is better for small coaching use because it avoids mandatory paid messaging APIs.

### Main fields

| Field | Type | Purpose |
|---|---|---|
| `_id` | ObjectId | Primary unique identifier |
| `teacherId` | ObjectId ref Teacher | Owner teacher |
| `studentId` | ObjectId ref Student | Student linked to reminder |
| `month` | String | Fee month |
| `recipientEmail` | String | Optional old email support |
| `recipientPhone` | String | Parent phone number |
| `message` | String | Reminder message sent/opened |
| `provider` | String | Default: `whatsapp_deeplink` |
| `providerMessageId` | String | For future paid provider integrations |
| `sentAt` | Date | Time reminder was logged |
| `status` | String enum | `opened`, `handled`, `sent`, or `failed` |
| `channel` | String enum | `whatsapp_manual`, `sms`, or `whatsapp` |
| `type` | String enum | `upcoming_due`, `overdue`, `partial`, or `manual` |
| `error` | String | Failure reason, if any |
| `createdAt` | Date | Auto-created |
| `updatedAt` | Date | Auto-updated |

### Index

```text
teacherId + month + recipientPhone + channel + type
```

This helps query reminder history by teacher, month, phone, channel, and reminder type.

### Interview explanation

> I store reminder attempts in NotificationLog. Since fully automated WhatsApp/SMS requires paid provider APIs and approval, I designed a practical manual WhatsApp reminder system. The backend prepares the message and WhatsApp link, and when the teacher opens or marks it handled, the app stores a log. This still gives accountability and history without paid automation.

## 12. Primary keys and foreign keys

MongoDB automatically creates `_id` for every document. This works like a primary key.

Example:

```text
Student._id = unique student identifier
```

For relationships, the app uses ObjectId references.

Example:

```text
FeeRecord.studentId = Student._id
FeeRecord.teacherId = Teacher._id
```

In SQL, these would be foreign keys. In MongoDB, they are references. MongoDB does not enforce them as strictly as SQL by default, so the application code must maintain integrity.

### Interview explanation

> MongoDB uses `_id` as the primary key. For relationships, I used ObjectId references like `teacherId` and `studentId`. These act like foreign keys at application level. Mongoose helps define references, but referential integrity is mainly handled by backend logic.

---

## 13. Referential integrity

Referential integrity means linked records should stay valid.

Example problem:

If a student is deleted, what happens to that student's:

- fee records?
- attendance records?
- notification logs?

In SQL, cascading delete can be handled by foreign key constraints.

In MongoDB, this project handles it in backend logic.

When a student is deleted, the backend also deletes related:

- FeeRecord documents
- Attendance documents
- NotificationLog documents

This prevents orphan records.

### Interview explanation

> Since MongoDB does not automatically enforce foreign key cascades like SQL, I handled referential integrity in my Express route. When a student is deleted, I delete that student's fee records, attendance records, and notification logs using `deleteMany`. This keeps the database clean.

## 14. Normalization vs embedding

MongoDB allows embedding documents inside other documents. But this project uses separate collections for repeated transactional data.

### Why not embed everything inside Student?

If all fees and attendance were stored inside the Student document, the document would grow continuously:

```text
Student
  attendance: many daily records
  fees: many monthly records
  notifications: many reminder records
```

This creates problems:

- student document becomes too large
- updates become more complex
- monthly fee reports become harder
- attendance analytics become harder
- indexes on nested arrays become more complicated

### Final design

Student stores stable profile data.

FeeRecord stores monthly fee transactions.

Attendance stores daily attendance.

NotificationLog stores reminder history.

Expense stores business expenses.

### Interview explanation

> I used a normalized-like design even though MongoDB is NoSQL. I did not embed fees and attendance inside the Student document because those records grow over time. Keeping them as separate collections makes queries, indexes, and analytics cleaner.

## 16. Indexing strategy

Indexes improve query speed. Without indexes, MongoDB may scan many documents to find matching records.

### Indexes used

Student:

```text
teacherId
class
teacherId + class + name
```

FeeRecord:

```text
teacherId
studentId
month
unique: teacherId + studentId + month
```

Attendance:

```text
teacherId
studentId
unique: teacherId + studentId + date
```

NotificationLog:

```text
teacherId + month + recipientPhone + channel + type
```

### Why these indexes matter

The app frequently asks questions like:

- show all students of this teacher
- show students by class
- get fee records for current month
- get attendance for a date/month
- check whether reminder was already logged

Indexes make these queries faster.

### Interview explanation

> I created indexes based on query patterns. Since almost every query is scoped by teacherId, I indexed teacherId. For fees and attendance, I used compound unique indexes to prevent duplicate records and improve lookup speed.

## 17. Authentication and data isolation

The project uses JWT authentication.

### Flow

1. Teacher logs in with email and password.
2. Backend verifies password using bcrypt.
3. Backend creates JWT token.
4. Frontend stores token.
5. Every protected API request sends token.
6. Backend middleware verifies token.
7. Backend attaches logged-in teacher to request.
8. Database queries use `teacherId`.

Example query idea:

```text
Find students where teacherId = logged-in teacher's id
```

This is very important for data privacy.

### Interview explanation

> I used JWT authentication and teacher-level data scoping. Even if the frontend requests data, the backend does not trust frontend filters. The backend takes teacherId from the verified JWT and uses it in MongoDB queries. This prevents one teacher from accessing another teacher's data.

## 18. Fee tracking design

Fee tracking is month-based.

Each student has a monthly fee amount stored in Student.

Each month, fee status is represented using FeeRecord.

### Status logic

```text
amountPaid = 0                 -> due
amountPaid > 0 but less fee    -> partial
amountPaid >= full fee         -> paid
```

### Receipt

When a payment is made, the system can generate a receipt number and frontend can generate printable receipt using jsPDF.

### Why month is `YYYY-MM`

The project stores month like:

```text
2026-08
```

This is easy to:

- display
- compare
- filter
- group in dashboard charts

### Interview explanation

> I modelled fees as monthly records. A compound unique index ensures one fee record per student per month. This gives a clean audit trail for fee status and makes monthly revenue calculation easy.

## 22. Reminder system database design

The project originally considered automatic email/SMS/WhatsApp reminders. But because SMS and WhatsApp automation usually require paid APIs and approval, the practical version uses manual WhatsApp reminders with logging.

### Reminder flow

1. Student has `feeDueDate`.
2. Backend checks current month fee status.
3. If fee is near due date, overdue, or partial, backend prepares reminder item.
4. Teacher opens WhatsApp with predefined message.
5. App logs the reminder action in NotificationLog.

### Why this is good for small coaching

- no paid SMS/WhatsApp API needed
- teacher stays in control
- still saves time because message is prefilled
- reminder history is stored
- parents receive message through normal WhatsApp

### Interview explanation

> I initially explored automated SMS/WhatsApp, but those require paid providers like Twilio and WhatsApp Business API approval. Since the target users are small coaching teachers, I designed a low-cost manual WhatsApp reminder system. The database still stores notification logs, so the teacher can track which reminders were opened or handled.

## 27. MongoDB Atlas challenges faced

During development, there were repeated MongoDB Atlas connection issues.

Common errors included:

```text
SSL routines: tlsv1 alert internal error
Could not connect to any servers in your MongoDB Atlas cluster
IP address is not whitelisted
```

### Why this happened

MongoDB Atlas protects the database using Network Access rules. Only whitelisted IP addresses can connect.

If the local internet provider changes the public IP address, Atlas may block the connection again.

This is common with dynamic IPs.

### Fixes used or suggested

1. Add current public IP in Atlas Network Access.
2. Check database username and password.
3. Check MongoDB URI in `.env`.
4. Use `tls: true`.
5. Use `family: 4` to force IPv4 when needed.
6. Increase `serverSelectionTimeoutMS`.
7. For local development, use local MongoDB or allow all IPs temporarily with strong password.

### Important security note

Using `0.0.0.0/0` in Atlas allows access from anywhere. It is convenient for development but less secure. If used, the database must have:

- strong password
- no secrets committed
- limited database user permissions
- production monitoring

### Interview explanation

> One challenge I faced was MongoDB Atlas IP whitelisting. My public IP changed, so Atlas blocked the connection. I learned that Atlas has network-level security. For development, I can either update my IP, use local MongoDB, or temporarily allow all IPs with strong credentials. For production, I would keep stricter access rules.

## 28. Why not SQL?

SQL could also work well for this project because the data has relationships.

For example:

- Teacher table
- Student table
- FeeRecord table
- Attendance table
- Expense table

But MongoDB was chosen because:

- the project is MERN-based
- JSON document format is easier with React/Express
- faster iteration while learning
- flexible fields for reminders and UI changes
- Mongoose gives enough schema control

### Honest comparison

SQL is stronger for strict relational constraints and complex joins.

MongoDB is simpler for flexible JSON-style app development.

In this project, relationships are still clear, but enforced mainly through backend logic and Mongoose.

### Interview explanation

> SQL would also be a valid choice because the project has relational data. But I chose MongoDB because it fits the MERN stack and allowed faster iteration. I still followed DBMS principles like primary keys, references, constraints, indexing, and normalization-style separation.

For reminders, I store history in NotificationLog and use a practical manual WhatsApp reminder flow because fully automated SMS/WhatsApp requires paid APIs.

> One real challenge I faced was MongoDB Atlas IP whitelisting. My public IP changed, so the database connection failed. I learned how Atlas network access works and how to solve it using current IP whitelisting, local MongoDB for development, or temporary all-IP access with strong credentials.

## 31. Interview Q&A

### Q1. Why did you use MongoDB?

I used MongoDB because the project is MERN-based and the data flows naturally as JSON between frontend, backend, and database. MongoDB also helped me iterate quickly while learning. To keep structure, I used Mongoose schemas, validation, references, and indexes.

### Q2. Is your MongoDB database schema-less?

MongoDB itself is flexible, but my application is not schema-less. I used Mongoose schemas to define fields, required values, enums, validation rules, timestamps, and indexes.

### Q3. What is the primary key in MongoDB?

Every MongoDB document has `_id`, which acts as the primary key. It is usually an ObjectId generated automatically by MongoDB.

### Q4. How did you represent foreign keys?

I used ObjectId references. For example, `studentId` in FeeRecord references the Student collection, and `teacherId` references the Teacher collection. These are like foreign keys, but MongoDB does not enforce them exactly like SQL, so the backend handles integrity.

### Q5. Why is FeeRecord separate from Student?

Fee records are monthly repeated data. If I embedded all monthly fees inside Student, the Student document would keep growing and analytics would become harder. A separate FeeRecord collection makes queries, updates, and monthly revenue calculation cleaner.

### Q6. How do you prevent duplicate fee records?

I used a compound unique index on `teacherId`, `studentId`, and `month`. This means one student can have only one fee record for a particular month under a teacher.

### Q7. How do you prevent duplicate attendance?

I used a compound unique index on `teacherId`, `studentId`, and `date`. So the same student cannot have two attendance records for the same day.

### Q8. How do you calculate pending fees?

For the current month, the backend calculates expected revenue from all students' fee amounts and subtracts the actual collected amount from FeeRecord records.

```text
pendingFees = expectedRevenue - monthlyRevenue
```

### Q9. How do you calculate net profit?

Net profit is calculated as:

```text
netProfit = monthlyRevenue - monthlyExpenses
```

Monthly revenue comes from FeeRecord `amountPaid`, and monthly expenses come from Expense `amount`.

### Q10. How do you handle authentication data?

The Teacher collection stores the login email and hashed password. Passwords are hashed using bcrypt before saving. JWT is used for login sessions. Protected routes verify the token and then use the teacher's id to query data.

### Q11. How do you keep each teacher's data separate?

Every major collection has `teacherId`. The backend gets teacherId from the verified JWT token and uses it in database queries. The frontend cannot decide teacherId manually.

### Q12. Did you use joins?

MongoDB does not use joins the same way SQL does. I used references and Mongoose queries. Where needed, I can use `populate` or aggregation. For dashboard analytics, I used aggregation to group revenue by month.

### Q13. What is aggregation in MongoDB?

Aggregation is MongoDB's way to process data through stages like match, group, sort, and project. In my project, I use aggregation to group fee records by month and sum collected revenue.

### Q14. What challenges did you face with MongoDB Atlas?

The main challenge was IP whitelisting. Atlas blocks connections from IPs that are not allowed. Since my public IP changed, I had to update Network Access. I also learned to check URI, username/password, TLS, and IPv4 settings.

### Q15. What would you improve in the database?

I would add transactions for critical multi-document operations, pagination for large lists, soft deletes, audit logs, more indexes, local MongoDB for development, and better backup/export features.

## 32. DBMS concepts used in this project

| DBMS Concept | How it appears in TuitionTrack |
|---|---|
| Entity | Teacher, Student, FeeRecord, Attendance, Expense, NotificationLog |
| Attribute | Fields like name, email, amountPaid, status |
| Primary key | MongoDB `_id` |
| Foreign key concept | ObjectId references like teacherId and studentId |
| One-to-many relationship | Teacher to Students, Student to FeeRecords |
| Constraints | Required fields, enums, min/max, regex |
| Unique constraint | Compound unique indexes |
| Indexing | teacherId, class, month, studentId indexes |
| Normalization | Separate collections for repeated data |
| Referential integrity | Backend deletes related records |
| Authentication data | Teacher with hashed password |
| Authorization | teacherId-based data access |
| Aggregation | Revenue chart and dashboard calculations |
